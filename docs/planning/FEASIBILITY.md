# CourseWatch 可行性研究

调研日期：2026-11-12（Asia/Shanghai）。范围：V2.0 需求及已确认的平台入口。本文记录调研阶段的研究与设计结论。

最新范围修订：jsjks 与人卫共同作为首批平台；jsjks 监控教学班内作业、考试的新发布与截止时间；学习通、雨课堂等优先整合现有实现；macOS 与 Windows 11 均为首版验收环境。原需求文件中的平台顺序只作为原始记录。

## 1. 结论与证据范围

**建议立项，但以单平台真实数据验证作为进入产品开发的门槛。** 独立后台、SQLite、任务差异检测、提醒、扩展管理界面都有成熟技术支撑；当前最大的未知是各平台登录会话能否稳定复用、任务能否完整读取及状态字段是否可靠。

当前证据分为三类：

| 类别 | 本次已完成 | 结论范围 |
| --- | --- | --- |
| 公开页面实测 | 人卫登录页、未登录作业入口、云南报名入口 HTTP 获取 | 入口存在、可观察到登录与跳转行为 |
| 上游静态证据 | 候选项目 README、固定提交的采集源码、许可证 | 有可供参考的采集路径及工程方案 |
| 已登录页面观察 | jsjks 教学班和编程作业列表已只读查看；人卫已有页面截图 | 可确认部分页面字段；尚无独立会话、接口与长期采集验证 |

没有测量常驻内存、CPU、安装体积、平台成功率、真实通知到达率。下文列出的验收条件属于后续实验设计，尚无对应性能结果。具体源码证据见 [开源选型](OPEN_SOURCE.md) 与 [来源索引](../research/README.md)。

## 2. 分项判断

| 需求 | 判断 | 关键条件 |
| --- | --- | --- |
| 浏览器关闭后持续监控 | 可行 | 用户级后台独立运行，不能由扩展负责长期调度 |
| Windows/macOS 自动启动、崩溃恢复 | 可行，需系统集成验证 | LaunchAgent / 用户登录计划任务，分别验证安装、退出、卸载行为 |
| 多平台任务统一管理 | 可行 | 标准任务模型保留来源差异与未知字段 |
| 平台登录一次长期使用 | 有条件可行 | 平台决定会话期限；必须支持重新登录和人工验证 |
| 所有平台均走 HTTP | 不成立 | 一些会话依赖浏览器上下文；需要按平台选择传输方式 |
| 人卫作业/考试采集 | 待验证 | 页面截图已确认作业列表的时间与状态列，考试、接口与 ID 待验证 |
| 学习通采集 | 有条件可行 | 有社区源码；需验证学校账号、分页、详情与状态 |
| 雨课堂采集 | 有条件可行 | 有社区源码；各区域域名、活动类型与分页需验证 |
| jsjks 教学班作业/考试 | 页面证据已有，后台采集待验证 | 主站教学班及编程作业列表已查看；图文作业、考试、接口与独立会话待验证 |
| MOOC、智慧树 | 尚未专项研究 | 保持后续候选，不纳入首版支持承诺 |
| 任务撤回自动识别 | 只在有明确证据时可行 | 未返回、课程归档、分页缺失均不能直接判撤回 |
| 关机/休眠期间实时监控 | 本地方案无法满足 | 需明确产品边界；恢复后补查无法还原所有中间变化 |
| 精确到秒的准时提醒 | 不作承诺 | 受系统休眠、进程运行与系统通知策略影响 |

Chrome 官方说明扩展 Service Worker 会因空闲等条件终止，支持把长期调度留在本地服务的架构选择。WebSocket 等机制可以延长部分运行时间，但不能解决浏览器退出问题。[官方说明](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)

## 3. 平台可行性

### 人卫：首批平台之一，技术风险应最先排除

- 已确认的平台入口：`https://tk.ipmph.com/exam/a/adminlogin`。
- 公开页面标题为“人民卫生出版社中国医学教育题库”。未登录访问需求中给出的 `/exam/a/exam/examTask`，最终到达登录页且返回 HTTP 200。
- 登录页源码出现人卫 SSO 地址、验证码脚本与设备相关脚本；只能据此确认依赖线索，不能认定每次登录都要求验证码或一定禁止自动化。
- 以“人卫 题库”为关键词的 GitHub 仓库搜索未返回匹配结果；该结果受搜索范围限制。

必须验证：用户自行登录后是否能只读查看作业和考试；两者是否不同入口；稳定任务 ID、详情时间、课程/班级范围、分页；独立会话在普通浏览器关闭和后台重启后是否仍可复用；是否影响用户正常登录。

后续页面截图已确认作业列表的开始时间、结束时间和状态等列，且侧栏有独立“我的考试”。开始时间不等同发布时间，序号不等同任务 ID。界面字段存在不代表已取得可稳定采集的数据接口。

**停止条件：** 无法获得授权只读数据、需人工验证而尚未完成，或独立会话不可复用。此时保留本地任务与异常提示，平台适配仍标记为待验证。

### 学习通：现有开源资料最充足

`xxt-Tool` 的源码包含课程列表、作业列表、考试列表及详情读取；`chaoxing-journal` 对部分成功、截止时间未知与人工验证状态进行了更细的建模。二者主要语言分别为 Kotlin、Dart，不是可直接安装到 Node.js 的适配器包。

建议将只读采集与解析逻辑移植为 TypeScript，使用 Cheerio 解析 HTML，同时重新验证接口响应与字段。不直接接入整套 Android/Flutter 应用。社区源码中记录的接口行为均不构成平台官方契约。

### 雨课堂：参考实现与覆盖完整性

`xxt-Tool/YtApi.kt` 包含课程、活动、近期考试等读取路径，接口按实际登录域名选择。其活动读取固定请求 `page=0&offset=100`，没有在该函数内遍历后续页；还有课程结束时间补截止时间、未知状态推断与首次观察时间近似提交时间等规则。

CourseWatch 应实现分页完整性、活动类型验证、时间来源标记；保留“未提供截止时间”和“无法确认提交状态”。不能根据任务标题含“测试”就认定它一定是考试。

### jsjks：按教学班内作业与考试适配

已确认的报名入口为 `https://jsjks.ynjy.cn/yncre/`。公开访问最终到 `/yncre/student/`，页面标识“云南省高校计算机等级考试报名”，包含学校选择、账号登录与校验字段。高校教务通知也指向这一入口。[公开页面证据](../research/platform-evidence.md)

监控范围进一步确定为教学班内作业、考试的发布与截止时间。公开报名页只能证明已核查入口的用途，不能据此判断登录后的教学功能范围。需核实教学班入口、班级范围、作业和考试列表、稳定 ID、发布时间与截止时间字段、分页及登录行为。

通过页面截图与已登录 Chrome 的只读观察，已定位主站教学课堂及编程作业路由，确认编程作业卡片存在时间区间、开放阶段和独立进度。在线考试菜单的路由已观察到，但内容未完成可靠核查。图文作业与课堂实验也有独立栏目，覆盖范围需逐项验证。详见[页面记录](../research/platform-evidence.md)。

范围包括发现新作业/考试、记录可读的发布时间、展示与提醒截止时间、检测截止时间修改。发布时间缺失时单独记录首次发现时间，不将其伪装为发布时间。报名、缴费、准考证不作为当前监控目标；不涉及作答或提交。

## 4. 原设计需要补充的地方

| 原设计 | 问题 | 建议 |
| --- | --- | --- |
| `fetchTasks(): Promise<RawTask[]>` | 无法表达失败、部分成功、合法空列表 | 返回带完整性与分区证据的采集结果 |
| `platform + platformTaskId` | 账号、学校、课程或任务类型间可能重号 | 加入本地账号、站点/租户与源命名空间，实测 ID 作用域 |
| 单一 `status` | 过期与已提交可同时成立 | 分开来源提交状态、本地时间状态、个人勾选状态 |
| 时间全用毫秒 | 不能表达未知、无期限、来源推断 | 统一存储单位，同时保存时区、原值与可信度 |
| `sourceHash` | 容易把倒计时等动态内容也当变化 | 对可追踪业务字段做规范化哈希，字段差异单独记录 |
| 任务未返回后撤回 | 无法排除归档、权限与分页变化 | 缺失进入待核实，仅明确撤回证据改变为取消 |
| 提醒去重键缺少规则/渠道 | 多条规则或渠道可能互相冲突 | 加入规则 ID、渠道 ID、规则版本与截止时间版本 |
| 任务、通知独立保存 | 崩溃时丢通知或重复通知 | 任务变更、历史、通知 Outbox 在同一事务写入 |
| 后台完整开发先于人卫验证 | 最大不确定性发现太晚 | 基础契约建立后立即开展人卫只读探索，提前验证系统通知 |
| Phase 3 依赖会话而 Phase 4 才做会话 | 阶段依赖倒置 | 将最小登录与会话持久化纳入首个平台探索阶段 |
| 假定 profile 受保护 | 文件权限不等于所有浏览器状态都已加密 | 令牌用系统凭据库；profile 限权，明确其保护边界 |
| V2.0 文档与 V0.x/V1.0 计划混用 | 文档版本与软件版本不清 | 保留需求记录，开发前明确应用版本序列 |

## 5. 运行、分发与成本

本地优先可免去统一云端数据库和账号系统，但安装、用户级自启动、系统通知身份、更新签名与浏览器运行时分发仍需工程投入。Windows、macOS 的真实安装验证都不可省略。

建议后台常态走授权只读 HTTP，Playwright 按需启动；不要默认每个平台常驻一个浏览器。某平台必须保持浏览器上下文时，单独测量资源占用与会话可靠性，再决定进程池和空闲回收策略。

长期运行采用低资源开销约束。首版据此排除常驻 Electron 宿主与常驻浏览器采集方案；若平台确实依赖长期浏览器保活，需记录为采集与资源约束冲突，不能默认启用重型后台。资源预算、浏览器回收及 24 小时测试方案见[轻量运行要求](RESOURCE_BUDGET.md)。

15 分钟扫描意味着每个平台每日约 96 次扫描。若一次扫描需 30 个 HTTP 请求，则约 2,880 请求/日/平台；这只是负载估算，不是平台允许的额度。应缓存稳定详情、错开平台、限制并发并遵从限流提示。若平台可接受间隔更长，应降低频率。

电脑关机时，即使启用 ntfy，CourseWatch 也不会产生新扫描结果；ntfy 只负责转发已生成的提醒。多设备持续监控需要额外的常开设备或服务，该部署模式需另行设计。

AI 不是首版可靠性前提。首次迭代用可解释规则完成任务归一与提醒；AI 摘要只能作为可选层，不能修改来源状态、猜测 DDL，或默认发送课程内容到外部模型。

## 6. 推进建议

1. 首先为 jsjks 与人卫分别验证“正常登录 → 完整只读快照 → 普通浏览器关闭后重查 → 独立后台重启后重查”；两者业务模型不同，不共享成功结论。
2. 同时验证 Windows/macOS 用户会话中的通知、自启动、安装与退出行为，系统能力按[跨平台方案](CROSS_PLATFORM.md)拆分。
3. 首批平台通过后实现核心一致性与最小扩展，再整合 MIT 现有实现中的学习通、雨课堂只读逻辑，不默认从零开发全部后续平台。
4. 各平台按能力发布。某个平台被阻塞时记录具体限制，不能用其他平台成功替代其验收。

阶段门槛和试验矩阵见 [整合与验证方案](INTEGRATION_PLAN.md)。目前可以确认架构具备实现路径，尚不能确认首批平台全部稳定可用。
