测试采用 100 条模拟个人日程，无账号、平台采集或模型调用。前台空闲不包含用户连续滚动、复杂图表或视频解码，不能直接代表真实课程学习负载。每状态预热 15 秒，安排 120 秒采样，取得 60 个点和 59 个约 2 秒 CPU 窗口；初次启动、最小化动画及恢复加载不在均值窗口中。前台 60/60 点有 WebView，最小化／关闭窗口均为 0/60。

最小化后的进程数为 2–3：WebView 已释放，但辅助进程有延迟回收。关闭主窗口时仅 AppKit 和 Node 两个进程，后台状态及提醒调度继续。CPU 仍含测试副本额外的每 0.5 秒控制／状态记录开销，分发应用没有这段测试代码。

## 测量方法与复现

- `scripts/measure-macos.py` 从当前生产 Swift 源码生成测试副本，仅改应用身份、端口 17401、临时数据目录和加入控制／状态记录；网页、Node、SQLite 及常规后台定时器沿用生产实现。通过 LaunchServices 启动，以免继承启动器的 WebKit 责任身份。
- 100 条日程写入 `.cache/macos-performance/data`，监控关闭；不读取正式数据库、浏览器资料、账号、Key 或题目。现有用户程序仅读取进程计数和资源。
- 用 macOS `responsibility_get_pid_responsible_for_pid` 与父子关系确定范围，包含外壳、Node、WebKit、Chrome 及可归属的解码 XPC，日常浏览器不计入应用资源范围。
- `proc_pid_rusage` 读取累计用户／系统 CPU 时间、RSS、physical footprint 和 package idle 唤醒。CPU=共同且启动标识不变的进程 CPU 时间差／墙钟时间，100% 为一逻辑核。间隔中退出的进程不完整计入，观察峰值不是连续监测的绝对峰值。
- RSS 相加可能重复计算共享页；physical footprint 是 macOS 内存记账指标，包含系统计入进程的资源，不能与 RSS 或 Windows privateBytes 直接互换。
- 每个状态报告 60 个点；均值、最小值、最大值及进程范围在文末 JSON。只测本机短时状态，不代表 10 分钟／24 小时稳定性、Intel Mac、Windows、真实采集峰值或所有课程。

```sh
npm run build:web
npm run build:server
python3 scripts/measure-macos.py
# 若另外需要功率：移走旧的 .cache/macos-performance 后运行
python3 scripts/measure-macos.py --with-power
```

临时诊断的管理员权限只用于本次功耗及只读进程归属探测；有权限的进程已结束，未改账户、sudoers 或应用权限，未安装常驻助手，已执行 `sudo -k`。最终完整进程资源复测使用普通用户权限。
