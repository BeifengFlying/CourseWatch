# 文案规范

**禁止 AI 化语言、无意义空泛口号、没有依据的宣传承诺。** 界面、通知、错误、项目文档和交付说明均须遵守。

## 写法

说明“是什么、能做什么、当前状态、接下来如何操作”，只写与当前内容有关的信息。页面标题使用内容名称，按钮使用操作名称，提示说明具体原因和可执行的下一步。

| 不采用 | 采用 |
| --- | --- |
| 今天，先做这些 | 待办事项 |
| 开启高效学习新篇章 | 添加日程 |
| 智能提醒，尽在掌握 | 提前 30 分钟提醒 |
| 打造无缝、极致的任务管理体验 | 关闭窗口后继续提醒 |
| 系统已全面优化，体验显著提升 | 任务标题从 13px 调整为 18px |
| 操作异常，请联系管理员 | 无法连接本地后台，请重新打开 CourseWatch |
| 我做这个项目，是想把任务放在一起 | CourseWatch 集中管理课程任务与个人日程 |
| 这是我手机上收到的邮件 | 手机端测试邮件接收示例 |
| 一键完成、标星和改提醒 | 支持完成标记、星标与提醒调整 |

“优化、提升、智能、优雅、极致、无缝”等词不能单独充当功能说明或结论。需要说明改了什么、什么条件下生效，以及有什么证据。

## 长度与语气

- 使用正式、客观、直接的书面表达，避免第一人称叙述、对话式开场、口语化评价、套话、无意义比喻与夸张形容词。正式表达不使用“现就有关事项说明如下”等公文套话。
- 适用范围包括中英文 README、使用与开发指南、需求方案、研究记录、更新日志及验证报告。英文采用相同的客观表述；第三方原文、许可证、原始引用、代码与日志保持原样。
- 操作步骤直接说明操作，功能说明使用产品或功能名称作为主语。功能约定和维护限制直接陈述规则，不叙述需求提出、确认或反馈的对话过程。
- 截图、日志及实机观察注明证据类型、日期和验证范围；素材注明文件名与处理方式，避免以提供者或对话参与者组织叙述。保留证据来源的差异，不将反馈记录改写为已实测结论。
- 验证记录注明日期、版本、环境、结果与未测范围，不使用交付对话代替记录。必要限制说明保留在对应位置，避免重复免责。
- 不为简单操作添加口号、副标题或大段说明。必要说明放在对应控件附近。
- 操作反馈写实际结果，例如“日程已保存”。失败提示写原因与下一步，不用含糊的“出了一点小问题”。
- 项目报告区分源码实现、模拟测试与实机验证，分别记录范围和结果。

## 提交前检查

读一遍可见文案，删去不提供功能、状态、操作或证据信息的句子。检查同一操作是否使用同一名称。与本规范冲突的新增文案应在交付前改写。
